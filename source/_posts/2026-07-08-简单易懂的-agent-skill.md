Agent Skill 是 2025 年以来 AI 编程工具领域最重要的标准化尝试之一。它用一种极简的格式，让 AI Agent 能够在需要时加载专业知识和操作流程。这篇文章将带你从零开始理解 Skill 是什么、怎么创建，以及它背后的工作原理。

<!--more-->

# 为什么需要 Skill

想象一个场景：你在公司里使用 AI 编程助手，每次部署代码前，都需要让 AI 帮忙执行一个数据库迁移脚本。问题是，这个迁移脚本是公司内部的，AI 不知道它的存在，也不知道正确的参数是什么。你每次都需要手动告诉 AI：「去执行 `python scripts/migrate.py --verify --backup`，记得先用 `--dry-run` 预览一下。」

如果能把这段知识「教会」AI，让它看到"部署"两个字就自动知道该怎么做，该多好。

这就是 Skill 要解决的问题。

Skill 本质上是一个包含 `SKILL.md` 文件的文件夹。它告诉 AI：**我是什么、什么时候用我、以及该怎么操作**。就像给 AI 配了一本随身携带的操作手册，需要的时候翻一翻，平时不占地方。

# 创建一个 Skill

## 最小的 Skill

一个 Skill 的最小结构非常简单，只有一个文件：

```
my-project/.agents/skills/deploy-migration/
└── SKILL.md
```

`SKILL.md` 的文件内容长这样：

```markdown
---
name: deploy-migration
description: 执行数据库迁移脚本。当用户提到「部署」「上线」「迁移数据库」
  或类似操作时使用。包含预览和验证步骤。
---

## 部署流程

1. 先预览变更：`python scripts/migrate.py --dry-run`
2. 向用户确认预览结果
3. 执行迁移：`python scripts/migrate.py --verify --backup`

关键注意事项：
- 永远不要跳过 `--dry-run` 步骤
- 如果预览显示有删除操作，必须额外向用户确认
- 生产环境的 `.env.production` 文件不要提交到 git
```

就这么简单。YAML 头部（frontmatter）的 `name` 和 `description` 是必填的，其余都是可选的 Markdown 正文。

但它已经实现了一个关键能力：**AI 不需要你每次都手动提示，看到"部署"这个关键词就会自动加载这份操作指南，然后按照里面的步骤来执行。**

## Skill 的完整结构

当技能变得更复杂时，一个 Skill 文件夹可以包含更多内容：

```
my-skill/
├── SKILL.md          # 必填：元数据 + 指令
├── scripts/          # 可选：可执行脚本
│   ├── validate.py
│   └── extract.sh
├── references/       # 可选：参考文档
│   ├── api-errors.md
│   └── schema.yaml
└── assets/           # 可选：模板、资源
    └── report_template.md
```

- **scripts/**：可以放 Python、Bash 等脚本。AI 在遵循 Skill 指令时可以直接调用它们。
- **references/**：补充文档。这些文件不会一次性加载，而是 AI 按需读取——比如"如果 API 返回非 200 状态码，请查阅 `references/api-errors.md`"。
- **assets/**：模板文件、配置文件等静态资源。

## Skill 的来源：知识从哪里来

创建 Skill 的第一个问题是：知识从哪来？好的 Skill 来自**真实经验**，而非凭空想象。

**从实际对话中提取。** 你在跟 AI 配合完成某项任务时，中间做了哪些纠正、用了哪些特定的工具、遇到了什么坑——把这些提取出来就是很好的 Skill 素材。关注几个关键点：

- **成功的步骤**：什么顺序做对了
- **你做的纠正**：比如"不要用库 X，用库 Y"，"记得处理 Z 这个边界情况"
- **输入输出格式**：数据怎么进来，怎么出去
- **上下文信息**：AI 原本不知道的项目特定事实

**从项目文档中合成。** 如果你有现成的内部文档、操作手册、API 规范、代码审查记录，可以把它们喂给大模型，让它合成一份 Skill。关键是材料要**项目特定**——一份基于你们团队真实事件报告的数据管道 Skill，远比一份基于通用"最佳实践"文章的 Skill 更有用。

**从基础库或通用能力中抽象。** 比如 PDF 处理、数据可视化这些通用能力，可以直接把常用工具和操作流程封装成 Skill。

如果拿不准从哪里开始，可以直接用 **skill-creator** 这个元技能来引导你——它是一个专门帮助你创建和优化 Skill 的 Skill，你只需要在 AI 对话中调用它，它会通过一系列问题引导你完成整个过程。

# 优化一个 Skill

创建初版只是开始。要让 Skill 真正好用，还需要经过迭代优化。这里我们以前面提到的 **skill-creator** 为例，看看一个专业的迭代流程是怎么做的。

## 测试-验证循环

skill-creator 的核心方法论是：**用测试驱动 Skill 的质量提升**。它的流程像一个微型的软件工程循环：

**第一步：准备测试用例。** 写 2-3 个真实的使用场景作为测试提示词。比如对于 PDF 处理 Skill，测试用例可能是：

- 「帮我把这份 PDF 里的文字提取出来」
- 「把这两份 PDF 合并成一份」

**第二步：并行运行对比测试。** 同时启动两组 AI——一组加载了你的 Skill，一组没有。让它们分别处理同一个测试用例。

**第三步：评分和对比。** 比较两组的输出质量和行为差异。有 Skill 的一组是不是确实做得更好？哪里还不够理想？

这一步的核心价值在于：**用数据而非感觉来判断 Skill 好不好用**。很多时候你觉得 Skill 写得不错，但实际对比下来发现改进空间还很大。

## 持续优化循环

拿到测试结果后，进入核心的优化循环：

1. **阅读 AI 的执行轨迹（而不仅仅是最终输出）。** 看 AI 在哪些步骤上浪费了时间、在哪一步犹豫不决、有没有执行了不该执行的指令。
2. **提炼通用模式，避免过拟合。** 如果 Skill 里写了太多针对测试用例的特定指令，换个场景就不灵了。好的 Skill 教 AI **怎么思考**，而不是**给出什么答案**。
3. **砍掉无效指令。** 执行轨迹中 AI 根本没用到、或者用了反而帮倒忙的指令，果断删掉。
4. **解释 Why 而不是只下命令。** 与其写「ALWAYS 使用 pdfplumber」这样的死命令，不如写「使用 pdfplumber 进行文本提取，因为它能更好地处理复杂表格。对于需要 OCR 的扫描件，改用 pdf2image + pytesseract」——AI 理解了原因，遇到不同场景才能做出正确判断。
5. **把重复出现的操作打包成脚本。** 如果你发现 AI 在每次执行时都独立写了同样的工具代码，就应该把它写到 `scripts/` 目录里，作为 Skill 的一部分。

每改完一轮，重新跑一遍测试，看分数变化。如此循环，直到满意为止。

## description 的优化

Skill 的 `description` 字段是整个 Skill 最关键的部分——因为它是**触发机制**。AI 在会话开始时只会加载所有 Skill 的 name 和 description，然后根据用户的问题判断「这个 Skill 是不是相关」。description 写得不好，再好的指令也永远不会被加载。

skill-creator 里面提供了一个专门优化 description 的流程：

1. **生成触发评测集。** 创建大约 20 个查询——一半是**应该触发**这个 Skill 的（比如「帮我提取 PDF 文字」），另一半是**不应该触发**的（比如「帮我给这个文档取个名字」），尤其是那些容易混淆的近邻场景。
2. **自动化测试。** 对每个查询运行三次（增加可靠性），看 Skill 是否被正确触发。程序会自动统计准确率。
3. **多轮迭代。** 程序会自动调整 description 的措辞，运行最多 5 轮优化，选出在测试集上表现最好的版本。

这个流程的价值在于：**description 的优化不是凭感觉拍脑袋，而是可以量化和自动化验证的。**

# Skill 在 Agent 中的工作原理

理解了怎么创建 Skill，我们再深入一层：**Agent 框架是怎么实现 Skill 支持的？** 这部分不要求你写代码，但理解原理会让你对 Skill 的能力边界有更清晰的认知。

## Agent 基础：从 Function Call 到现代 Agent

在聊 Skill 的嵌入之前，先回顾一下 AI Agent 的基本工作方式。

**最早的 Function Call（函数调用）**：大模型本身只能输出文字。但很多时候我们需要它执行操作——比如查数据库、发邮件、执行命令。Function Call 的机制就是：开发者提前注册一批"工具"（每个工具有名称、描述、参数定义），当用户的问题需要调用工具时，模型不回答文字，而是输出一个结构化的函数调用请求。框架层执行这个请求，把结果返回给模型，模型再根据结果继续回答。

一个经典的 Function Call 工具定义长这样：

```json
{
  "name": "get_weather",
  "description": "获取指定城市的天气信息",
  "parameters": {
    "city": { "type": "string", "description": "城市名称" }
  }
}
```

模型收到「北京今天天气怎么样？」后不会直接编造天气，而是返回 `get_weather(city="北京")`。框架执行后把结果返还，模型再组织成自然语言回答用户。

**ReAct 模式（Reasoning + Acting）**：Function Call 是单步的。ReAct 把它扩展成了多步循环——模型可以思考（Reasoning），然后执行操作（Acting），观察结果，再思考，再操作……直到最终给出答案。

这就是今天大多数 AI 编程助手的核心循环：**思考 → 读文件 → 思考 → 改代码 → 思考 → 运行测试 → 给出结果**。

**现代 Agent 框架**：在 ReAct 之上，现代 Agent 框架还加了很多东西——上下文管理（对话长了怎么办）、权限控制（哪些操作需要用户确认）、子代理（复杂任务拆成多个子任务并行处理）、以及我们今天重点讨论的 **Skill 系统**。

## Skill 的三层渐进式加载

Skill 接入 Agent 的核心设计理念叫做 **渐进式披露（Progressive Disclosure）**——只在需要时才加载更多信息，概念简单但非常实用：

| 层级 | 加载内容 | 加载时机 | Token 消耗 |
|------|---------|---------|-----------|
| 第一层 目录 | name + description | 会话开始时 | 每个 Skill 约 50-100 token |
| 第二层 指令 | SKILL.md 完整正文 | Skill 被激活时 | 建议 < 5000 token |
| 第三层 资源 | scripts/、references/、assets/ | 指令中引用了这些文件时 | 视情况而定 |

这个设计的巧妙之处在于：**即使你装了 20 个 Skill，AI 在对话开始时也只需要付出大约 1000-2000 token 的额外成本**。它只是知道有哪些技能可用，只有真正用到的才会加载完整指令。

下面我们详细看这个过程的每一步。

## 第一步：发现 Skill

Agent 启动时，会扫描几个特定目录，寻找包含 `SKILL.md` 文件的文件夹：

```
~/.agents/skills/                 # 用户级：跨项目通用
├── pdf-processing/
│   └── SKILL.md                  ← 被发现
├── data-analysis/
│   └── SKILL.md                  ← 被发现
└── README.md                     ← 被忽略

my-project/.agents/skills/        # 项目级：跟着代码仓库走
└── deploy-migration/
    └── SKILL.md                  ← 被发现
```

两个关键设计：

- **项目级优先于用户级**：如果两个位置有同名 Skill，项目级的会覆盖用户级的。这意味着团队可以在 repo 里放项目特定的 Skill，它会自动覆盖个人的同名配置。
- **`.agents/skills/` 是跨工具通用目录**：最初由 Anthropic 提出，现在已被 GitHub Copilot、Cursor、Gemini CLI、OpenAI Codex 等众多工具采用。一个 Skill 写好后无需修改就能在不同工具间通用。

## 第二步：解析 SKILL.md

找到 `SKILL.md` 后，框架只提取 **name** 和 **description** 两个字段——其余先不动。这就像图书馆的目录卡片，你不需要读完每本书才知道它是讲什么的。

```
发现 3 个 Skill：
  - pdf-processing：「提取 PDF 文字，填写表单，合并文件」
  - data-analysis：「分析数据集，生成图表」
  - deploy-migration：「执行数据库迁移脚本」
```

总 token 消耗：大约 150-300。极低成本。

## 第三步：构建 Skill 目录并注入

框架把这些信息组织成一个结构化的列表，放在系统提示（System Prompt）或者专门的工具描述里，告诉模型：「以下是一些可用的技能，如果你觉得相关，可以加载完整说明。」

用最简单的 System Prompt 方式，大概是这样的效果（实际格式因框架而异）：

```
<available_skills>
  <skill>
    <name>pdf-processing</name>
    <description>提取 PDF 文字，填写表单，合并文件。处理 PDF 相关任务时使用。</description>
  </skill>
  <skill>
    <name>deploy-migration</name>
    <description>执行数据库迁移脚本。当用户提到「部署」「上线」「迁移」时使用。</description>
  </skill>
</available_skills>

当任务匹配某个 skill 的描述时，请使用文件读取工具加载对应的 SKILL.md 获取完整说明。
```

同时，模型被告知：**「当你的任务匹配某个 Skill 的描述时，去加载它的完整内容。」** 这个"加载"可以有两种实现方式：

- **文件读取模式**：模型直接用自己的读文件工具去读 `SKILL.md`。最简单，几乎零开发成本。
- **专用工具模式**：框架注册一个专门的 `activate_skill` 工具，模型调用它来激活 Skill。好处是可以加入权限控制、使用统计、去重等逻辑。

## 第四步：激活 Skill

用户说「帮我把这份 PDF 里的表格提取出来」。

模型看到「PDF」这个关键词，扫描目录中的 Skill 描述，发现 `pdf-processing` 的 description 正好匹配，于是它激活这个 Skill——要么读取 `SKILL.md` 文件，要么调用专门的激活工具。

**加载完 Skill 指令后，模型的"行为模式"就变了。** 它不再用自己的通用 PDF 知识（那可能是过时或者不适用于当前环境的知识），而是严格按照 Skill 里写的步骤来操作——使用指定的工具、执行指定的验证脚本、甚至注意到那些文档里特别标注的「坑」。

这就是 Skill 的核心价值：**把"通用能力"替换成"特定领域的正确做法"。**

## 第五步：管理 Skill 的上下文生命周期

Skill 指令加载后，还有一个容易被忽略但很重要的问题：**上下文管理。**

对话越长，上下文窗口越满。很多 Agent 框架会自动压缩或裁剪早期的对话内容（因为 token 有上限）。如果不做特殊处理，Skill 指令就可能在下一次自动裁剪时被丢掉——模型失去了这些指令，却还在"假装"使用这个 Skill，结果是行为悄悄退化，用户完全不知情。

所以一个好的 Skill 实现需要：

- **保护 Skill 内容不被裁剪**：把 Skill 激活时注入的内容标记为"受保护"，上下文压缩算法会跳过它。
- **去重**：如果模型或用户不小心重复激活了同一个 Skill，框架应该检测到并跳过，避免同样内容在对话里出现多次。
- **子代理委派（高级特性）**：对于一些特别复杂的 Skill 工作流，有些框架支持把 Skill 的执行委派给一个独立的子代理——子代理在一个干净的上下文里运行，只带着 Skill 指令和相关工具，完成后把结果返回给主对话。这样既能隔离上下文，又能并行执行。

# 总结

回顾整篇文章，核心脉络其实很简单：

1. **Skill 是一个标准化的知识包**——一个文件夹 + 一个 `SKILL.md` + 可选的脚本和参考文件。它让 AI 能在恰当的时机加载恰当的领域知识。
2. **创建 Skill 从真实经验出发**——从你和 AI 的实际对话中提取有效模式，或者从项目文档中合成专门知识。初版之后用测试-对比-优化的循环不断打磨，description 更是可以量化优化到最优触发率。
3. **Agent 框架接入 Skill 的核心是渐进式披露**——先给目录、匹配后加载指令、按需读取资源。三步的 token 成本递增，确保"装得多但用着不卡"。
4. **Skill 生态正在形成标准**——从 Anthropic 最初提出这个格式，到现在 Claude Code、Cursor、GitHub Copilot、Gemini CLI、OpenAI Codex 等几十个工具共同支持。一个 Skill 写好了，换工具不用重写。

Skill 本质上是把"个体经验"变成了"可共享的知识"。当每个人都可以把自己的专业知识封装成 Skill，当每个团队都可以把项目规范变成 Skill 随代码一起分发，AI 编程助手的能力边界就不再受限于通用训练数据——它会变得真正了解你的项目、你的领域、你的做事方式。
